# Steering スキル

作業指示ごとに、要求（requirements.md）、設計（design.md）、タスクリスト（tasklist.md）を作り、tasklist.md に沿って TDD で実装する。

- 置き場所: `.sdd/steering/[YYYYMMDD]-[機能名]/`
- 永続ドキュメント（`.sdd/` の PRD、機能設計書、アーキテクチャ設計書、リポジトリ構造定義書、用語集）には、プロジェクト全体の方針を書く。ステアリングファイルには、この作業で何をどう作るかを書く。方針は永続ドキュメントを参照し、ステアリングファイルに書き写さない。
- ステアリングファイルは「最終的にどう作ったか」を表す。計画と違ったら design.md と tasklist.md を実装に合わせて直す。変更の経緯は git に任せる。
- ドキュメントは日本語で書く。

## 計画

1. 永続ドキュメントを読む（ないものは飛ばす）。
2. `./templates/` の requirements.md、design.md、tasklist.md をもとにステアリングファイルを作る。当てはまらない節は削除する。
3. 次の順に埋める。
   1. requirements.md の受け入れ条件に `AC-n` の番号を付ける。
   2. design.md の公開 API に、受け入れ条件を満たすのに必要なものだけを書く。
   3. 公開 API ごとにテストケースを書く（下の「テストケース」に従う）。
   4. design.md の「テストの4本柱での確認」を確かめ、満たさないテストケースを直す。
   5. tasklist.md を、公開 API のスタブとテスト（Red まで）のフェーズと、実装（Green → Refactor）のフェーズに分ける。テストのサブタスクには design.md のテスト名を写す。
4. 開発に必要なツールや設定ファイル（例: `pyproject.toml`、アーキテクチャ設計書の品質ゲートを動かすツール、Claude Code のフック）がなければ、それを用意するタスクを最初に入れる。
5. 実装できるタスクだけを入れる。将来やるかもしれないことや検討中のことは入れない。モジュールを足すなら、依存ルールのチェックツールの設定、アーキテクチャ設計書、リポジトリ構造定義書の更新もタスクにする。

## テストケース

クライアントから観察できる振る舞いだけをテストにする。

- 操作は公開 API の呼び出しだけにする。
- 結果は、戻り値、送出される例外、出力（例: HTTP ならステータスとボディ、CLI なら出力と終了コード）だけで確かめる。
- 状態の変化は、別の公開 API で読み直して確かめる。
- プライベートなメソッドや属性、呼び出し回数、内部の協力者のモック、DB の中身は確かめない。

テストの4本柱（退行に対する保護、リファクタリングへの耐性、迅速なフィードバック、保守のしやすさ）を満たすこと。

## 実装

tasklist.md の上から順に、アーキテクチャ設計書の方針に従って進める。

- スタブ: 公開 API のシグネチャと、送出する例外の名前だけを書く。内部のヘルパーのためのクラスは作らない。
- Red: テストを書いて実行し、想定どおりの理由で失敗することを確かめる。モジュールの読み込みエラー（例: Python なら ImportError）や書き間違いで落ちているなら Red ではない。Red を確かめる前に実装を書かない。
- Green: テストを通す最小限の実装をする。
- Refactor: テストが通ったまま整理する。振る舞いは変えない。

### 進捗の記録

進捗の正式な記録は tasklist.md とする。

- タスクを終えたら、その場で `[ ]` を `[x]` にする。着手しただけでは `[x]` にしない。Red はテストが想定どおりに失敗したとき、Green はテストが通ったときが完了。
- サブタスクがあるタスクは、サブタスクがすべて `[x]` になってから `[x]` にする。
- 計画と変わったら、tasklist.md と design.md を直す。
  - やり方を変えたタスクには理由を書き添える（例: `- [x] タスク名（実装方法を変更: 理由）`）。
  - 不要になったタスクは打ち消し線を引き、理由を書く（例: `- [x] ~~タスク名~~（不要になった理由）`）。
  - 必要になったタスクは足す。
- 今後も守る規約や方針が決まったら、アーキテクチャ設計書に書き足す。
- 新しい用語が出てきたり言い方を変えたりしたら、用語集に書き足す。

### 報告

フェーズや作業の区切りで、design.md が作ったものと合っているか確かめて直し、次を報告する。

- 何を作ったか
- 計画から変えた点、不要になったタスク
- 永続ドキュメントに書き足したこと
