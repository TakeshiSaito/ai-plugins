# 用語集作成ガイド

## 基本原則

### 1. 1つの意味に1つの言い方

**悪い例**:
```
PRD: 「タスクを完了にする」
機能設計書: 「Todo を終了する」
コード: close_item()
```

**良い例**:
```
| タスク | `Task` | 利用者がやることを1件ずつ記録したもの | Todo、アイテム | 機能設計書のデータモデル「タスク」 |
| 完了 | `TaskStatus.DONE` | タスクをやり終えた状態 | 終了、クローズ | 機能設計書のデータモデル「タスク」 |
```

ドキュメント、コード、画面や出力で、同じものを同じ名前で呼ぶ。

### 2. 定義は短く、詳しいことは参照する

**悪い例**:
```
| タスク | `Task` | 利用者がやることを1件ずつ記録したもの。タイトルは1〜100文字で、同じプロジェクトの中で重複できない。削除するとコメントも消える | Todo、アイテム | なし |
```

**良い例**:
```
| タスク | `Task` | 利用者がやることを1件ずつ記録したもの | Todo、アイテム | 機能設計書のデータモデル「タスク」 |
```

属性や制約は機能設計書に書く。2か所に書くと、片方だけ更新されて食い違う。

### 3. 載せるのは迷う言葉だけ

広く知られた技術用語（HTTP、SQLite など）は載せない。
プロダクト固有の言葉と、このプロジェクトで特別な意味で使う言葉だけを載せる（YAGNI）。

## 作成の流れ

### ステップ1: 用語を拾う

- PRD の機能とユーザーストーリーから、名詞（データや役割）と動詞（操作）を拾う
- 機能設計書のデータ、コンポーネント、例外の名前を拾う
- アーキテクチャ設計書とリポジトリ構造定義書から、特別な意味で使う言葉（レイヤーの名前など）を拾う

### ステップ2: 言い方を決める

- 同じ意味で別の言い方をしているものを1つにまとめ、残りを「使わない言い方」に書く
- 機能設計書で使っている名前を優先する。コードの名前と合わせやすいため

### ステップ3: 永続ドキュメントを直す

- 「使わない言い方」を永続ドキュメントで探し、用語集の言い方に直す

## チェックリスト

- [ ] プロダクト固有の用語に、コード上の名前がある
- [ ] 定義が1〜2文で、定義の中で使う用語も用語集に載っている
- [ ] 同じ意味の用語が2つ載っていない
- [ ] 永続ドキュメントで「使わない言い方」が使われていない
- [ ] 属性、型、制約、例外クラス、状態の移り方を書き写していない（機能設計書で扱う）
- [ ] 広く知られた技術用語を載せていない
