# PRD作成スキル

ユーザーが渡したメモから、PRD を一度で作る。アイデアの壁打ちはしない。

## 入力

- ユーザーが指定したファイル（例: `draft.md`）、または会話に貼られた文章
- 置き場所は決まっていない。指定がなければ、どのメモを使うかユーザーに聞く

## メモの扱い

メモは、PRD を作ったら開発者が消す前提とする。

- メモは読むだけにする。編集、移動、削除はしない。
- PRD の本文でメモのファイル名を参照しない（「draft.md 参照」とは書かない）。
- メモにある必要なことは、すべて PRD に移す。PRD だけ読めば足りる状態にする。
  - 技術的な決めごと（フレームワーク、DB、設計方針など）は「前提と制約」に移す。後続の機能設計書とアーキテクチャ設計書はここを読んで引き継ぐ。
  - 参考リンクは「参考資料」に移す。

## 既存ドキュメントの優先順位

既存のプロダクト要求定義書があれば、その構造と内容を保ったまま、メモの内容を足して更新する。

## 出力先

```
.sdd/product-requirements.md
```

テンプレート: ./template.md

## 作成の流れ

### 1. メモを読む

機能、技術的な決めごと、参考リンク、作らないものを拾い出す。

### 2. テンプレートに沿って PRD を書く

- 「目的」には、何のためのツールかを2〜4文で書く。
- 機能は、ユーザーストーリー、受け入れ条件、優先度にする。受け入れ条件は確かめられる形で書く（「速い」ではなく「1,000件の一覧取得が1秒以内」）。
- 当てはまらない「該当する場合」の節は削除する。
- メモに書かれておらず推測では決められないことは、埋めずに「未決事項」に書く。質問はしない。

### 3. 取り込み漏れを確かめる

メモの項目ごとに、PRD のどこに移したかを対応表にして会話で示す（ファイルには残さない）。
移していない項目があれば PRD に足す。

### 4. 報告する

次を伝えて終える。

- 「未決事項」の一覧
- 「メモの内容は PRD に移したので、不要になったら削除してください」

## 優先度

- **P0（必須）**: これがないと目的を果たせない
- **P1（重要）**: P0 のあとすぐに欲しい
- **P2（できれば）**: いつか欲しい

メモで優先度が分からない機能は P1 にし、「未決事項」に書く。

## 要求と設計を分ける

PRD には「何ができるか」を書く。テーブルの形、クラスの分け方、エンドポイントの細部は機能設計書で決める。
ただしメモで決まっている技術的な方針は、「前提と制約」に残す。
