# 機能設計書作成スキル

PRD（`.sdd/product-requirements.md`）の「何を作るか」を、データ、コンポーネント、入口、エラーの形に落とす。

- 出力先: `.sdd/functional-design.md`
- テンプレート: ./template.md。当てはまらない節（DB を使わなければテーブル、CLI がなければ CLI など）は削除する。
- 既存の機能設計書があれば、その構造と内容を保ったまま更新する。
- 技術スタックとレイヤー構成はアーキテクチャ設計書で扱う。設計の作法（レイヤーの分け方、DDD を採るかなど）はこのスキルでは決めず、アーキテクチャ設計書に方針があれば従う。
- この設計書にはプロジェクト全体の設計を書く。作業ごとのテストケースや実装の手順は、ステアリングファイルに書く。

## 決めごと

### データ

- 属性ごとに型と制約（文字数、使える文字、範囲など）を書く。
- DB を使う場合は第三正規形以上にし、崩すなら理由を書く。一意制約、外部キー、削除時の扱い（RESTRICT / CASCADE）を決める。

### コンポーネント

- 公開 API は、PRD の機能に必要なものだけにする。内部のヘルパーは書かない。
- シーケンス図は込み入ったユースケースだけに描く。単純な作成・取得・更新・削除は、コンポーネントの表だけでよい。

### HTTP API（該当する場合）

- リソースは複数形の名詞にし、`/api` の下に置く。子のリソースは `/api/{親}/{親の id}/{子}` にする。
- 作成は POST で 201 と作ったものを返す。変更と削除は 204 で何も返さない。
- 一部の属性だけを変える操作は `PUT /api/{リソース}/{id}/{属性}` にする。
- エラーのボディは `{"detail": "..."}` にそろえる。

### CLI（該当する場合）

- コマンドと、それが呼び出す関数を1対1にする。データを変えたコマンドは、何をしたかを1行出力する。

### エラー

- エラーを意味で分けて例外クラスを作り、言語の標準の例外を継承する（例: Python なら `LookupError`、`ValueError`、`RuntimeError`）。
- 例外と入口での扱いの対応は、この設計書のエラーハンドリングの表にまとめる。HTTP API なら、見つからないは 404、既にあるは 409、入力が不正は 422 にする。
- メッセージは、何がどうだったかが1行で分かるようにする（例: `project foo does not exist`）。
