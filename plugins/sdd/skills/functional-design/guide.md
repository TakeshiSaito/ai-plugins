# 機能設計書作成ガイド

PRD をもとに、システム構成、データモデル、コンポーネント、ユースケース、入口を設計する手順。

## 機能設計書の目的

- PRD の「何を作るか」を、「どう作るか」に置き換える
- 実装の前に、データの形、コンポーネントの責務と公開 API、API の形を決めておく
- 受け入れ条件とテストを結び付ける

## 作成の流れ

### ステップ1: PRD を読む

- P0（必須）の機能と受け入れ条件を拾い出す
- 「前提と制約」にある技術的な決めごとを確かめる
- 機能に出てくる名詞（データの候補）と動詞（操作の候補）を書き出す
- 用語が揺れていたら、ここで1つに決める。用語集があれば、その言い方を使う（言い方は用語集で決める）

### ステップ2: システム構成図を描く

- 利用者、入口（HTTP API、CLI など）、主なコンポーネント、データの保存先を Mermaid で描く
- アーキテクチャ設計書にレイヤー構成があれば、それに合わせる

### ステップ3: データモデルを決める

- 名詞ごとに、属性、型、制約（文字数、使える文字、範囲など）を表に書く。実装では pydantic の `Field` などで表す
- 複数のデータにまたがるルール（同じ名前を使えない、など）も書く

DB を使う場合:

- テーブルを決め、ER図を描く。
- 多対多の関係（記事とタグなど）は中間テーブルにし、関係に付く値（タグを付けた日時など）は中間テーブルのカラムにする。
- 一意制約と外部キー、削除時の扱い（RESTRICT か CASCADE か）を決める。
- 正規化の確認の表を埋める。第三正規形以上を基本とし、崩すときは理由を書く。

### ステップ4: コンポーネントを設計する

- 動詞を、コンポーネントの公開 API（関数やメソッド）にする（`create_project`、`list_projects` など）
- それぞれに、責務、引数と戻り値の型、送出する例外、依存先を書く
- 公開 API は、PRD の機能に必要なものだけにする（YAGNI）。内部のヘルパーは書かない

### ステップ5: ユースケースを描く

- 込み入ったユースケースだけシーケンス図を描く。単純な作成・取得・更新・削除は、コンポーネントの表だけでよい

### ステップ6: 入口を決める（該当する場合）

HTTP API を持つ場合の例:

- リソースは複数形の名詞にし、`/api` の下に置く。
- 作成は POST で 201 と作ったものを返す。変更と削除は 204 で何も返さない。
- 一部の属性だけを変える操作は、`PUT /api/{リソース}/{id}/{属性}` にする。
- 子のリソースは `/api/{親}/{親の id}/{子}` にする。
- エラーのボディは `{"detail": "..."}` にそろえる。

CLI を持つ場合の例:

- コマンドと、それが呼び出す関数を1対1にし、データを変えたコマンドは何をしたかを1行出力する。

### ステップ7: エラーハンドリングを決める

- エラーを意味で分け、それぞれの例外クラスを決める。標準の例外を継承すると、入口での扱いをまとめて決めやすい
- 入口ごとの扱いを決める。HTTP API の場合の例:

| エラーの種類 | HTTP ステータス |
|------------|---------------|
| 見つからない（`LookupError`） | 404 |
| 既にある | 409 |
| 入力が不正（`ValueError`、検証エラー） | 422 |

- メッセージは、何がどうだったかが1行で分かるようにする（例: `project foo does not exist`）

### ステップ8: テスト観点を書く

PRD の受け入れ条件ごとに、それを確かめるテストの名前を `test_<動作>_<対象>_<条件>_<結果>` で書く。
正常系だけでなく、例外になる場合も書く。

## レビュー観点

- [ ] PRD の P0 の機能が、すべてコンポーネントの公開 API になっている
- [ ] データの属性、型、制約がはっきりしている
- [ ] DB を使う場合、テーブルが第三正規形以上になっている、または崩した理由がある
- [ ] DB を使う場合、一意制約、外部キー、削除時の扱いが決まっている
- [ ] すべての公開 API に、送出する例外が書かれている
- [ ] 例外と入口での扱い（HTTP ステータスや終了コードなど）の対応がある
- [ ] 受け入れ条件とテストが結び付いている
- [ ] 技術スタックやレイヤー構成を書いていない（アーキテクチャ設計書で扱う）
