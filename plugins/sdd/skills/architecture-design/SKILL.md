# アーキテクチャ設計スキル

PRD と機能設計書を読み、技術スタック、レイヤー構成、依存ルールなど、プロジェクト全体の技術的な方針を決める。

- 出力先: `.sdd/architecture.md`
- テンプレート: ./template.md。当てはまらない節は削除する。
- 既存のアーキテクチャ設計書があれば、その構造と内容を保ったまま更新する。
- この設計書にはプロジェクト全体の方針を書く。作業ごとの設計は、ステアリングファイルに書く。
- ディレクトリ構成とファイルの命名規則は、リポジトリ構造定義書で扱う。

## 決めごと

### 技術選定

- PRD の「前提と制約」にある技術的な決めごとに従う。決まっていないものは選び、理由を書く。
- ライブラリは、広く使われ、継続的にメンテナンスされているものに限る。

### レイヤー構成

- レイヤーの分け方はこのスキルでは決めない。プロジェクトに合うもの（例: 入口 / サービス / データアクセス、ポートとアダプター）を選び、理由を書く。小さく始め、必要になってからレイヤーを足す。
- モジュール依存表は、依存ルールのチェックツールの設定にそのまま書き写せる形にする。

### 実装の差し替え

- データの保存先や外部サービスなど、差し替えたいもの（テストでの差し替えを含む）がある場合だけ、抽象と DI を使う。
- 抽象と実装の対応は、1か所（DI コンテナなど）にだけ書く。

### 設定

- アプリ全体の設定と、特定の技術の設定を分けて置く。
- データやログの置き場所は1つの設定を基準に決め、テストでは一時ディレクトリに向ける。

### 永続化（DB を使う場合）

- 一意制約と外部キーが DB で効くようにする（例: SQLite なら接続ごとに `PRAGMA foreign_keys = ON`）。
- DB の例外は、データアクセスの中で、機能設計書で決めた例外に変換する。
- スキーマの作り方（起動時にまとめて作るか、マイグレーションツールを使うか）と、その理由を書く。

### ログ

- ログの出力先の構成は1か所にまとめる。
- データを変えた処理は、何をしたかを1行ログに残す。

### テスト

- 本物の依存先（一時ディレクトリの SQLite など）でテストし、テストで動かせない外部の処理だけを偽物に差し替える。
- カバレッジの下限（既定は 70%）を決め、品質ゲートで強制する。

## 作成後にすること

- モジュール依存表と、依存ルールのチェックツールの設定が食い違っていないか確かめる。設定がまだない、または中身が空なら、依存表から書き起こす。
- 技術スタックの表と、依存の定義ファイルが合っているか確かめる。
