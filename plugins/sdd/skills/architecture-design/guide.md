# アーキテクチャ設計ガイド

## 基本原則

### 1. 技術選定には理由を書く

**悪い例**:
```
- FastAPI
- SQLAlchemy
```

**良い例**:
```
- FastAPI
  - リクエストとレスポンスを pydantic のモデルで検証できる
  - Swagger UI が自動で付き、API を手で試せる
- SQLAlchemy
  - SQLite から別の DB へ移るときに、データアクセスの実装を差し替えるだけで済む
```

### 2. ライブラリは有名で信頼できるものに限る

広く使われていて、継続的にメンテナンスされているものだけを選ぶ。
既定の構成で足りるなら、新しいライブラリを足さない（YAGNI）。

### 3. レイヤー間の依存の向きを決め、機械的に確かめる

どのレイヤーがどのレイヤーに依存してよいかを表にし、`tach.toml` で確かめる。
レイヤーの分け方そのものは、プロジェクトの規模と要件に合わせて選ぶ。

### 4. 要件は測定できる形で書く

「速い」ではなく「100件の一覧取得が 200ms 以内」のように書く。

## 既定の技術スタック

特に理由がなければ、次を使う。

| 分類 | 技術 | 用途 |
|------|------|------|
| 言語 | Python（uv で使える最新の安定版） | |
| パッケージ管理 | uv（ビルドは `uv_build`） | 依存の管理、仮想環境、コマンドの実行 |
| データの検証 | pydantic | データの型と制約、入力の検証 |
| 設定 | pydantic-settings | 環境変数と `.env` からの設定の読み込み |
| DI | dependency-injector | 差し替える実装の組み立てと注入 |
| 永続化（DB を使う場合） | SQLAlchemy + SQLite | データの保存と取得 |
| HTTP API（該当する場合） | FastAPI + uvicorn | 入口 |
| テスト | pytest、pytest-cov、httpx2 | テスト、カバレッジ、`TestClient`（HTTP API を持つ場合） |
| リント | ruff | |
| 型チェック | ty | |
| モジュール境界 | tach | 依存の向きと外部依存のチェック |

## レイヤー構成

### 決めること

レイヤーごとに、名前、置き場所、責務、依存してよいレイヤーを表に書く。
小さく始め、必要になってからレイヤーを足す（YAGNI）。

### 例1: 入口 / サービス / データアクセス

| レイヤー | 置き場所 | 責務 | 依存してよいもの |
|---------|---------|------|-----------------|
| 入口 | `{package}/{入口}.py` | 入力の受け付けと検証、結果の表示や応答 | サービス |
| サービス | `{package}/services/` | 機能の処理 | データアクセス |
| データアクセス | `{package}/storage/` | データの保存と取得 | なし |

- 入口はデータアクセスを直接呼ばない。
- サービスは入口に依存しない。

### 例2: ポートとアダプター

データの保存先や外部サービスを差し替えたい場合の構成。

| レイヤー | 置き場所 | 責務 | 依存してよいもの |
|---------|---------|------|-----------------|
| コア | `{package}/{機能}.py` | 機能の処理と、外部とのやりとりの抽象（`ABC`） | なし |
| アプリケーション | `{package}/applications/` | 入口から呼ばれる処理の単位 | コア |
| 出口のアダプター | `{package}/{技術}/` | 抽象の実装（例: SQLite） | コア、設定 |
| DI コンテナ | `{package}/installer.py` | 実装の組み立て | アプリケーション、出口のアダプター、設定 |
| 入口 | `{package}/{入口}.py` | 入力の受け付けと検証、結果の表示や応答 | アプリケーション、DI コンテナ |

### 依存ルールを tach.toml にする

設計書のモジュール依存表を、そのまま `tach.toml` に書き写す。

```toml
[[modules]]
path = "{package}.services"
depends_on = ["{package}.storage"]

[[modules]]
path = "{package}.storage"
depends_on = []
```

## 実装の差し替え（該当する場合）

データの保存先や外部サービスなど、差し替えたいもの（テストでの差し替えを含む）がある場合だけ、抽象と DI を使う。

- 差し替えたいものだけを `ABC` で抽象にし、実装を別のモジュールに置く。
- 抽象と実装の対応は、DI コンテナ（例: `{package}/installer.py` の `DeclarativeContainer`）にだけ書く。
- 実装を使う関数は `@inject` と `Provide["<プロバイダー名>"]` で受け取る。`wiring_config` には、`Provide` を使うモジュールを並べる。
- 入口は起動時に DI コンテナを作る。初回の起動で用意するデータ（サンプルなど）があれば、ここで作る。

## 設定

- アプリ全体の設定（ホーム、ホスト、ポートなど）は `{package}/env.py` の `Env` に、特定の技術の設定は、その技術のモジュールの `〜Env` に置く。
- 環境変数の接頭辞は `{PREFIX}_`、特定の技術の設定は `{PREFIX}_{技術}_` にする。
- データやログの置き場所は `{PREFIX}_HOME` を基準にし、テストでは一時ディレクトリに向ける。
- 設計書には、環境変数、既定値、内容の一覧を書く。

## 永続化（DB を使う場合）

- テーブルは機能設計書のデータモデルに合わせ、第三正規形以上にする。
- 一意制約と外部キーは DB でも張る。SQLite では `PRAGMA foreign_keys = ON` を接続ごとに有効にする。
- DB の例外（`IntegrityError` など）は、データアクセスの中で、機能設計書で決めた例外に変換する。
- スキーマの作り方（`create_all` か、マイグレーションツールか）と、その理由を書く。

## ログ

- ロガーはパッケージ名で取り、`{package}/log.py` でファイルへの出力を構成する。
- データを変えた処理は、何をしたかを1行ログに残す。

## テスト戦略

| 対象 | 置き場所 | 方法 |
|------|---------|------|
| 公開 API（関数、メソッド、エンドポイント、コマンドなど） | `tests/test_<モジュール>.py` | 本物の依存先（一時ディレクトリの SQLite など）を使う。HTTP API は `TestClient` で呼ぶ |

- カバレッジの下限（既定は 70%）を `test.sh` の `--cov-fail-under` で強制する。
- テストで動かせない外部の処理（プロセスの起動など）だけを、テスト用の偽物に差し替える。

## 品質ゲート

| チェック | コマンド | どこで動かすか |
|---------|---------|--------------|
| テスト | `./test.sh` | 作業の終わり、CI |
| リント | `uv run ruff check .` | Claude Code の Stop フック、CI |
| 型 | `uv run ty check` | Claude Code の Stop フック、CI |
| モジュール境界 | `uv run tach check`、`uv run tach check-external` | Claude Code の Stop フック、CI |

- [ ] すべての技術選定に理由がある
- [ ] レイヤーごとの置き場所、責務、依存してよいレイヤーが書かれている
- [ ] レイヤー構成を選んだ理由がある
- [ ] モジュール依存表が `tach.toml` と一致している
- [ ] 設定の一覧（環境変数、既定値、内容）がある
- [ ] 例外と入口での扱い（HTTP ステータスや終了コードなど）の対応がある
- [ ] テストの種類、置き場所、カバレッジの下限が決まっている
- [ ] 性能などの非機能要件が測定できる形で書かれている
